# ECOMAJES

Python Streamlit application.

## Run & Operate

- `streamlit run app.py --server.port 5000` — run the ECOMAJES Streamlit app (workflow "Streamlit App", port 5000); entry point is `app.py`, config in `.streamlit/config.toml` (do not change server settings)
- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- `app.py` — entry point; wires session init, login gate, and navigation only
- `ecomajes/config.py` — source of truth for roles, sedes, and the navigation tree (`get_navigation(role, sede)`, `get_sedes(role)`); uses `Page` (leaf) and `Group` (sub-menu) dataclasses
- `ecomajes/auth.py` — password requirements per role (reads env vars `ECOMAJES_ADMIN_PASSWORD`, `ECOMAJES_GERENCIA_PASSWORD`)
- `ecomajes/session.py` — session-state helpers (login/logout, active page)
- `ecomajes/login.py` — login screen (role + sede + password); sede options depend on role
- `ecomajes/navigation.py` — role/sede-based sidebar (flat + grouped) + `ROUTES` table mapping page keys to real views; unlisted pages fall back to the placeholder
- `ecomajes/db.py` — PostgreSQL data layer (psycopg2 pool via `DATABASE_URL`); products + movements with atomic stock updates (`register_movement`, raises `StockError`)
- `ecomajes/views/inventario.py` — worker-friendly product list (uses `db.list_catalog_products` scoped by sede + `material_tipo`): columns Código/Descripción/Categoría/Unidad/Stock/**Estado** (Estado from stock: Agotado if stock≤0, Stock bajo if stock_minimo>0 and stock≤stock_minimo, else Disponible — matches `alertas.py`), a search box (código/descripción via the `search` param) and Categoría + Estado filters (applied in Python). Keeps the "Agregar producto" form for editable roles. Shared by `op_inventario` / `adm_mn_inventario` / `adm_msu_inventario`
- `ecomajes/views/movimientos.py` — register entrada/salida/venta (updates stock) + recent movements. Uses plain widgets (NOT `st.form`) so the sale-type selector and precio sugerido react live. Ventas pick a **Tipo de venta** (Unidad/Metro/Centímetro/Corte personalizado — plancha_completa intentionally excluded from this UI). Unidad = original auto-price flow (snapshots `prices.precio`). Metro/Centímetro/Corte personalizado = special flow showing Cantidad vendida, Precio sugerido (read-only = suggested unit price × cantidad), Precio final, Autorizado por Gerencia, Observación; **Observación is required for Corte personalizado**. Special sales pass `precio_final` → stored as `precio_total` (so Balance/Reporte de Ventas/Historial use Precio final automatically), plus `tipo_venta`, `autorizado_por` and `nota`=Observación. No sobrantes/cutting calcs. Does NOT touch the prices module. Success shown via a `mov_flash` session-state message after rerun; input keys cleared on success
- `ecomajes/views/importar_productos.py` — Importar Productos module (page `ger_importar_productos`, GERENCIA-only; the single sanctioned nav addition). Uploads an **.xlsx** (legacy `.xls` intentionally not accepted — `xlrd` isn't installed), normalizes headers case-insensitively (aliases in `_COLUMN_ALIASES`: CODIGO/DESCRIPCION/UNIDAD/PRECIO DE VENTA SOLES/COSTO INICIAL SOLES/FAMILIA/CATEGORIA), dedups repeated Código in-file (`_dedupe`, keeps the fullest DESCRIPCION + first non-empty precio/costo/familia, reports skipped duplicates), previews the normalized rows, then calls `db.import_products`. **PRECIO/COSTO/FAMILIA are now persisted**: PRECIO DE VENTA SOLES → `prices.precio` (+`precio_sugerido`), COSTO INICIAL SOLES → `prices.costo`, FAMILIA → `products.familia`. These are stored for pricing/future filters+reports but deliberately NOT shown in the worker Inventario screen or the Precios sheet UI (no UI change). GERENCIA picks Sede destino + Tipo de material for NEW products; existing códigos update wherever they live. **Preview** (`_preview_rows`) shows Código/Descripción/Familia/Categoría/Unidad/Precio de Venta/Costo Inicial/Stock Inicial (categoría marked "(auto)" when empty/invalid → uses `db.resolve_categoria`). **Confirmation** shows Filas en el archivo/Productos únicos/Duplicados a omitir + two buttons **✅ Importar Productos** / **❌ Cancelar** (Cancelar aborts with no changes). **Summary** shows Productos nuevos/actualizados/Duplicados omitidos/Errores encontrados/Tiempo de importación (via `time.perf_counter`). Best-effort `db.log_audit(AUDIT_IMPORT, ...)`
- `ecomajes/views/precios.py` — mini-Excel price sheet (`st.data_editor`): edit + save prices per product; used automatically for future ventas
- ÁREA ADMINISTRATIVA navigation (in `config.py`): each material section has the same 6 items in this order — Registro de Movimiento (`movimientos`), Inventario (`inventario`), Gestión de Inventario (`productos`, create/edit/deactivate), Alertas (`alertas`), Reporte de Ventas (`reporte_ventas`), Historial (no view yet → placeholder). Sede Principal shows Material Nuevo + Material Segundo Uso; Sucursal shows Material Nuevo only. No generic "Reportes" for ADMINISTRATIVA (Reportes is GERENCIA-only). Page keys: `adm_mn_*` / `adm_msu_*` (registro_movimiento/inventario/gestion_inventario/alertas/reporte_ventas/historial)
- `ecomajes/views/alertas.py` — Alertas module (pages `adm_mn_alertas`, `adm_msu_alertas`; ÁREA ADMINISTRATIVA). Replenishment alerts scoped to the current sede (`ctx["sede"]`, never all sedes) and material type. Lists active products that are Agotado (stock ≤ 0) or Stock bajo (stock_minimo > 0 and stock ≤ stock_minimo), each rendered as a card with Código/Descripción/Categoría/Estado + Stock actual/Stock mínimo/Cantidad sugerida a pedir (= max(stock_minimo − stock, 0)) metrics and a **"Solicitar Reposición"** button. The button calls `db.add_replenishment_request` (status Pendiente); products that already have an open request show "Solicitud enviada" instead (via `db.open_replenishment_product_ids`). Reads `db.list_catalog_products` — never mutates inventory/stock
- `ecomajes/views/solicitudes_reposicion.py` — Solicitudes de Reposición module (page `ger_solicitudes_reposicion`, GERENCIA-only, role-guarded). Lists every replenishment request (filterable by estado) in an overview table (Fecha/Producto/Código/Sede/Stock actual/Stock mínimo/Cantidad sugerida/Solicitado por/Estado) plus per-request status editors. GERENCIA moves each request through Pendiente → En proceso → Comprado → Recibido via `db.set_replenishment_status`. Only manages purchase requests — never changes inventory quantities
- `ecomajes/views/reporte_ventas.py` — sales report (pages `adm_mn_reporte_ventas`, `adm_msu_reporte_ventas`): filter by period (Día/Semana/Mes/Año) + location (Principal/Sucursal/Empresa Completa); shows totals via `db.financial_summary`; add optional daily expenses + observations
- `ecomajes/views/balance.py` — Balance Financiero + Dashboard (page `ger_balance_financiero`, GERENCIA): single screen with filters (ubicación/rango de fechas/categoría), 8 KPI cards (ventas día/mes, gastos día/mes, utilidad neta, productos vendidos, stock bajo, agotados), charts (ventas por día/mes, productos más/menos vendidos, ventas por sede, ingresos vs gastos, inventario por categoría), and an alerts block (stock bajo, agotados, comentarios pendientes placeholder, últimos movimientos). KPI cards use the location filter with fixed día/mes periods; the date-range + category filters drive the charts. Reuses existing data only (venta movements, expenses, stock, prices) — no data duplication
- `ecomajes/views/reportes.py` — Reportes module (page `ger_reportes`, GERENCIA): period-based reports (Día/Semana/Mes/Año) for Sede Principal / Sucursal / Empresa Completa + optional categoría. `_gather(f)` builds one report payload (KPIs + tables) reused by both the on-screen render and the exports (no duplication): total ventas/productos/ingresos/gastos/utilidad, movimientos del período (`db.list_movements_range`), stock bajo/agotados, más/menos vendidos, and chart tables (ventas por día/mes/sede, ingresos vs gastos, inventario por categoría). Reuses existing read-only db functions only
- `ecomajes/reporting.py` — export helpers `build_excel(report)` (multi-sheet .xlsx via pandas + openpyxl) and `build_pdf(report)` (landscape A4 via reportlab); pure formatting of a report payload, no DB access. Requires `openpyxl` + `reportlab` (in requirements.txt)
- `ecomajes/views/comentarios.py` — Comentarios module (pages `op_comentarios`, `adm_comentarios`, `ger_comentarios`; all roles). Any role creates a comment (fecha auto, usuario=rol, ámbito/ubicación, texto, estado default Pendiente). GERENCIA (detected via `ctx["usuario_rol"] == config.ROLE_GERENCIA`) additionally sees response + status controls (Pendiente/En revisión/Atendido). Uses `db.add_comment/list_comments/respond_comment/set_comment_status`
- `ecomajes/views/auditoria.py` — Auditoría module (page `ger_auditoria`, GERENCIA-only, read-only). Role-guarded view of the audit trail with filters (acción/módulo/rango de fechas). Columns: fecha, usuario, rol, acción, módulo, detalles. Uses `db.list_audit` + `db.list_audit_modules`
- `ecomajes/views/_placeholder.py` — shared placeholder page for not-yet-built menu entries
- Audit logging is woven into existing modules at success points via best-effort `db.log_audit(...)` (never raises): login (`login.py`), product create/edit/deactivate/activate (`productos.py`), price save (`precios.py`), inventory movement (`movimientos.py`), expense (`reporte_ventas.py`), payroll payment (`recursos_humanos.py`), and report download (`reportes.py`, via `download_button` `on_click` so it logs only on an actual click, not per render)

## Data model

- `products` (id, sede, material_tipo ['nuevo'|'segundo_uso'], nombre, sku, unidad, stock, created_at); unique on (sede, material_tipo, nombre). Catálogo de productos fields also live here (products IS the inventory/catalog table): `codigo` (partial-unique when not null), `descripcion`, `categoria`, `tipo_venta` (CHECK-constrained: 'unidad'|'metro'|'centimetro'|'plancha_completa'|'corte_personalizado', default 'unidad'), `peso`, `stock_minimo` (>= 0, default 0), `observaciones`, `activo` (bool, default true = Estado activo/inactivo). `unidad` is the existing column reused for Unidad. Sale-type keys/labels are defined in `db.py` (`VENTA_*`, `TIPO_VENTA_LABELS`). Corte personalizado stores only the sale type + observaciones for now (no cutting calculations yet). `familia` (TEXT, nullable) stores the imported FAMILIA for future filters/reports; it is written by the importer but not shown in any current UI
- `movements` (id, product_id→products, tipo ['entrada'|'salida'|'venta'], cantidad, nota, usuario_rol, sede, created_at, precio_unitario, precio_total, tipo_venta, autorizado_por); on a plain-unit `venta` the unit price is snapshotted from `prices` into `precio_unitario`/`precio_total`. `tipo_venta` (CHECK: NULL or one of the VENTA_* keys) records the sale type on ventas (defaults to `unidad`); `autorizado_por` (nullable TEXT) records who authorised a special sale. For special sales (metro/centímetro/corte personalizado) the caller passes `precio_final` → stored as `precio_total` (Precio final) with `precio_unitario` = precio_final/cantidad; Observación is stored in `nota`. `register_movement(..., tipo_venta=None, precio_final=None, autorizado_por=None)` keeps the old signature working (legacy/unit venta unchanged). Sales = venta movements (source of truth for the sales report); all report aggregations SUM `precio_total`, so Precio final flows through automatically
- `prices` (id, product_id→products UNIQUE, codigo, descripcion, categoria, unidad, peso, precio, p1, p2, p3, precio_minimo, precio_sugerido, `costo`, observaciones, created_at, updated_at); one row per product, upserted via `db.save_prices`. `costo` (NUMERIC, nullable) stores the imported COSTO INICIAL SOLES; it is written only by the importer (`_upsert_import_price`) and is intentionally NOT part of the Precios `st.data_editor` UI (so `save_prices` never touches it)
- `expenses` (id, fecha, descripcion, monto, sede, usuario_rol, created_at); daily expenses per location, feed `db.financial_summary` net-income and future Balance Financiero
- `daily_observations` (id, fecha, sede, observacion, usuario_rol, created_at); optional daily notes per location
- `comments` (id, created_at, usuario_rol, ambito/ubicación, texto, estado ['pendiente'|'en_revision'|'atendido'], respuesta, respondido_por, respondido_at); status labels/constants in `db.py` (`COMMENT_*`, `COMMENT_STATUS_LABELS`). Any role inserts; only GERENCIA sets `respuesta`/`estado`
- `replenishment_requests` (id, created_at, product_id→products ON DELETE SET NULL, codigo, descripcion, sede, material_tipo, stock_actual, stock_minimo, cantidad_sugerida, solicitado_por, estado ['pendiente'|'en_proceso'|'comprado'|'recibido'], CHECK-constrained + indexed on estado); purchase requests created from ALERTAS. Status keys/labels in `db.py` (`REPO_*`, `REPO_STATUS_LABELS`); an "open" request is any state except `recibido`. `db.add_replenishment_request` skips creating a duplicate when the product already has an open request (returns False). Read via `db.list_replenishment_requests`; status changed via `db.set_replenishment_status`; `db.open_replenishment_product_ids` powers the ALERTAS "already requested" state. This table NEVER affects `products.stock`
- `audit_log` (id, created_at, usuario_rol, accion, modulo, detalle); append-only activity trail. Action keys/labels in `db.py` (`AUDIT_*`, `AUDIT_ACTION_LABELS`). Written only through best-effort `db.log_audit` (swallows all exceptions so it can never break the primary action). Read via `db.list_audit(accion, modulo, date_from, date_to)` + `db.list_audit_modules()`. Since login is by role (no per-user identity), `usuario` == `rol`
- `db.import_products(rows, sede, material_tipo)` — Excel importer upsert used by Importar Productos. Matches on globally-unique `codigo` (partial-unique index enables identity across sedes): existing codigo → UPDATE descripcion(fullest)/categoria/unidad + `familia`=COALESCE(new, existing); missing codigo → matched by `nombre` (=descripcion) within (sede, material_tipo); new → INSERT with nombre=descripcion (on a `(sede,material_tipo,nombre)` collision it appends ` (codigo)` to keep nombre unique) RETURNING id. Per-row SAVEPOINT so one bad row can't abort the batch. `db.classify_categoria(descripcion)` auto-buckets into `IMPORT_CATEGORIES` (TUBO RECTANGULAR/REDONDO/CUADRADO, PLANCHAS, PLATINAS, ANGULOS, DISCOS, EPP, MALLAS, ALAMBRES, PERNERIA, CERRAJERIA, OTROS) via ordered keyword rules (`_CATEGORY_RULES`) matched at a **word boundary** (regex `\b`, accents folded) so short abbreviations like ANG/RED/PLAT don't false-match (e.g. MANGUERA↛ANG, PARED↛RED). `db.resolve_categoria(provided, descripcion)` keeps the Excel category only when it's a valid `IMPORT_CATEGORIES` member (case-insensitive), otherwise auto-classifies — used by both the preview and `import_products`. **Pricing/cost**: when a row supplies precio_venta and/or costo, `_upsert_import_price` upserts `prices` by product_id — precio→`precio`/`precio_sugerido`, costo→`costo`, seeding codigo/descripcion/categoria/unidad; all fields use COALESCE so it never wipes precio/costo/sheet-only fields (p1/p2/p3/precio_minimo/peso/observaciones) the user curated in Precios, and rows without precio/costo create NO price row (backward compatible). `_import_decimal` tolerates `S/` and thousands separators
- `db.financial_summary(sede, include_all_sedes, date_from, date_to)` — shared aggregate (total_sales, total_products, total_revenue, total_expenses, net_income); reusable by Balance Financiero later
- Stock is stored on `products.stock` and mutated only via `db.register_movement` inside a `SELECT … FOR UPDATE` transaction; entrada adds, salida/venta subtract, negative stock is rejected
- Schema is created in the dev DB via SQL; production schema is applied by Replit's Publish flow (do not write migration scripts or startup DDL)

## Architecture decisions

- Roles/sedes/modules and access are centralized in `config.py`; module→render mapping lives in `navigation.py` to keep `config.py` import-free (avoids circular deps)
- Auth is scaffolded (not yet hardened): passwords come from env vars with dev fallbacks. "Simple vs strong password" is currently expressed by the configured values, not an enforced strength policy
- GERENCIA selects a sede for data context but gets all modules regardless of sede

## Product

ERP for a steel & hardware company (acero y ferretería). Three roles — OPERARIOS (no password), ÁREA ADMINISTRATIVA (password), GERENCIA (password) — each with role/sede-scoped modules. Business logic per module is built incrementally, one module at a time, after approval.
